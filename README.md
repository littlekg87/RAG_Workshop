# 세종실록으로 만드는 RAG 워크숍

**한국어** · [English](README.en.md)

세종실록 XML을 활용해 **검색 증강 생성(Retrieval-Augmented Generation, RAG)** 시스템을 직접 만드는 워크숍입니다. 이론 설명과 Colab 실습을 번갈아 진행하며, 자료가 청크와 벡터로 바뀌고 검색 근거를 거쳐 답변이 되는 과정을 살펴봅니다.

이 워크숍이 강조하는 것은 단순한 챗봇 구현을 넘어선 **데이터에 맞춘 설계**입니다. 자료의 맥락을 읽고, 의미가 유지되도록 나누고, 검색 결과와 답변을 원문에 비추어 평가하는 과정에 인문학자의 전문성이 필요합니다.

## 준비와 실행

1. 위의 **Open in Colab** 버튼으로 노트북을 엽니다. Google 계정과 인터넷 연결이 필요합니다.
2. 코드를 실행하기 전에 **런타임 → 런타임 유형 변경 → T4 GPU**를 선택합니다.
3. `sejong_xml.zip`을 컴퓨터에 다운로드합니다.
4. 노트북의 **1-1 셀부터 순서대로** 실행합니다. 설치 완료 메시지를 확인한 뒤 다음 셀로 이동합니다.
5. **2-1 셀**의 업로드 창에서 `sejong_xml.zip` 한 개를 선택합니다.
6. 청킹·임베딩·검색·생성 셀을 실행한 뒤, **7단계**에서 Gradio 화면으로 질문합니다.

공개 모델을 Colab에 직접 다운로드해 실행합니다. **유료 모델 API, API 키, Google Drive 연결을 사용하지 않습니다.** 무료 Colab의 GPU가 할당되면 유료 API 없이 실습할 수 있지만, GPU 할당과 세션 지속 시간은 보장되지 않습니다. 런타임이 삭제되면 모델·데이터 준비를 다시 수행해야 합니다.

## 무엇을 배우나요?

발표는 다음 여섯 부분으로 구성됩니다.

1. RAG의 정의, 할루시네이션, 검색·증강·생성의 관계
2. 라이브러리 설치와 GPU 모델 준비
3. XML 구조, 청킹, 메타데이터, 임베딩과 벡터 DB 구축
4. 질문 임베딩, 코사인 유사도·내적, top-k, 프롬프트와 답변 생성
5. Gradio 프론트엔드와 검색·생성 백엔드의 연결
6. 검색 실패와 생성 실패, 각 단계의 개선 방법과 상호 관계

발표자료에는 전체 셀 코드, 복사 버튼, 코드 해석 팝업, 단계별 강조와 시각화가 들어 있습니다. 일부 시각화는 개념 설명용 예시이며, 실제 임베딩·검색 결과와 구분해 표시했습니다.

## 실습의 7단계

| 단계 | Colab 셀 | 하는 일 |
| --- | --- | --- |
| 1. 기본 세팅 | 1-1, 1-2 | 라이브러리 설치, GPU 확인, E5와 Qwen3 다운로드·로딩 |
| 2. XML 청킹 | 2-1, 2-2 | ZIP 업로드, 기사 추출, 긴 본문 분할, 메타데이터 보존 |
| 3. 벡터 DB 구축 | 3-1, 3-2, 3-3 | 청크 임베딩 → 숫자 배열 확인·저장 → FAISS 인덱스 구축 |
| 4. 질문 임베딩 | 4 | 문서와 같은 E5 모델로 질문을 벡터화하고 정규화 |
| 5. 검색 | 5 | 정규화 벡터의 내적으로 유사도를 계산하고 상위 k개 청크 검색 |
| 6. 답변 생성 | 6 | 규칙·검색 근거·질문을 구성해 Qwen3로 답변 생성 |
| 7. 프론트엔드 | 7 | Gradio에서 질문·top-k를 받아 답변과 전달된 근거 표시 |

Raw data를 청킹 가능한 XML로 만드는 전처리는 사전에 완료된 상태로 시작합니다. 실습에서는 제공된 XML의 기사를 읽고 청크를 만듭니다.

## 모델과 실행 위치

| 구성 | 역할 | 실행 위치 |
| --- | --- | --- |
| `intfloat/multilingual-e5-small` | 청크와 질문을 384차원 벡터로 변환 | GPU |
| `Qwen/Qwen3-1.7B` | 검색 근거와 질문으로 한국어 답변 생성 | GPU · float16 |
| FAISS `IndexFlatIP` | 정규화 벡터의 내적으로 정확 검색 | CPU |
| Gradio | 웹 화면의 입력·출력을 Python 함수에 연결 | Colab 서버 / 브라우저 화면 |

문서에는 `passage: `, 질문에는 `query: `를 붙입니다. 양쪽 벡터를 길이 1로 정규화하므로 **내적이 코사인 유사도와 같습니다.** FAISS가 각도를 직접 구하거나 벡터를 회전시키는 것은 아닙니다.

워크숍 기본 실습에서는 모델을 추가 학습하지 않습니다. 파인 튜닝·하이브리드 검색·재순위화는 품질 개선을 위한 확장 방향으로 소개합니다.

## 데이터와 기본 설정

- **범위:** 세종 즉위년부터 32년까지의 연대기 XML 33개. 오례·악보·지리지 등은 실습 ZIP에 포함하지 않습니다.
- **기사:** 30,948개. 일부 기사만 제한해서 쓰지 않고 전체 연대기를 처리합니다.
- **검색 텍스트:** 한국어 기사 제목 + 한문 본문.
- **청킹:** E5 토크나이저 기준 본문 350토큰, 겹침 40토큰. 기사 경계를 넘어서 합치지 않습니다.
- **청크:** 기본 설정과 제공 ZIP에서 37,126개. 입력·설정을 바꾸면 개수도 달라집니다.
- **메타데이터:** 기사 ID, 제목, 날짜 코드, 분류, 판본·권책·면, 파일명, 분할 번호.
- **임베딩:** 배치 크기 32, 384차원, 길이 1로 정규화.
- **검색:** 기본 `top-k=3`. Gradio에서는 1–5개를 선택합니다.
- **생성:** 전달할 검색 근거는 Qwen 토크나이저 기준 최대 5,000토큰, 새 답변은 최대 256토큰입니다. 규칙·질문·대화 형식은 근거 분량 제한과 별도로 붙습니다.

날짜 코드와 출처는 원문 값을 보존합니다. 예를 들어 `1418-08-11L0`를 그대로 양력 날짜로 해석하지 않습니다. 자료의 원문·국역 확인에는 [국사편찬위원회 조선왕조실록](https://sillok.history.go.kr/)을 참고하세요.

## 결과를 읽을 때

유사도 점수는 **정답 확률이 아닙니다.** 유사한 다른 사건이 상위에 검색될 수 있고, 올바른 근거를 찾았어도 작은 생성모델이 한문이나 예외 조건을 잘못 해석할 수 있습니다.

Gradio가 표시하는 출처는 **모델에 실제로 전달한 검색 근거**입니다. 답변의 모든 주장이 검증되었다는 뜻은 아닙니다. 이전 대화를 기억하는 챗봇도 아니며, 새 질문마다 검색과 생성이 다시 이루어집니다.

답변을 개선하려면 원자료, 청킹, 임베딩 모델, 질문 규칙, 색인과 검색 방식, 근거 구성, 생성모델을 함께 살펴야 합니다. 한 단계의 변경은 다른 단계의 입력과 한계에도 영향을 줍니다.
